.. _auditing:

Auditing
========
NVFLARE has an auditing mechanism to record events that occur in the system. Both user command events
and critical job events generated by the learning process are recorded.

The audit logging system is primarily implemented in :class:`Auditor<nvflare.fuel.sec.audit.Auditor>`.

Audit File Locations
^^^^^^^^^^^^^^^^^^^^
The audit files are located in different directories depending on the process type:

1. Server Parent (SP) Audit Log:
   - Located in the server's root workspace directory
   - Contains system-level events for the server

2. Server Job (SJ) Audit Log:
   - Located in the job's workspace directory
   - Contains job-specific events for the server

3. Client Parent (CP) Audit Log:
   - Located in the client's root workspace directory
   - Contains system-level events for the client

4. Client Job (CJ) Audit Log:
   - Located in the job's workspace directory
   - Contains job-specific events for the client

To access the audit files for a job, run `download_job <job_id>` and look in the downloaded job's workspace folder
for the SJ and CJ logs (by default named ``audit.jsonl``). Existing audit, log and result
directory overrides continue to determine the output location. Use a full job download: an outputs-only
download intentionally omits audit files.

Audit File Format
^^^^^^^^^^^^^^^^^
JSON (JavaScript Object Notation) represents a record as named values. JSONL (JSON Lines) stores one JSON
record per line. Each audit event is a JSON object, and every field value is a string. Embedded line breaks,
quotes and other special characters are escaped by JSON encoding, so an event occupies one physical line.

UTC (Coordinated Universal Time) is the shared time standard used for new event timestamps. A timestamp
contains the year, month and day separated by hyphens, the letter ``T`` separating the date from the time,
hours, minutes and seconds separated by colons, and six fractional-second digits following a period.
The final ``+00:00`` indicates an offset of zero hours and zero minutes from UTC.

Event Fields
^^^^^^^^^^^^
Field names use snake_case: lowercase words separated by underscores. The following mapping uses the
established meanings of the documented field codes. No additional event information is introduced.

.. csv-table::
    :header: Documented code,Field name,Meaning
    :widths: 10, 20, 70

    E,event_id,Identifier of the event
    T,timestamp,UTC time of the event with an explicit timezone offset
    U,user,Name of the user
    A,action,User-issued command or the existing combined task name and task identifier
    J,job,Identifier of the job
    S,scope,Name of the job scope
    R,reference,Supplied reference value
    M,message,Optional message describing the event

Ordinary command events always include ``event_id``, ``timestamp``, ``user`` and ``action``.
Job events always include ``event_id``, ``timestamp`` and ``job``. The optional fields ``reference``,
``scope`` and ``message`` are omitted when their supplied values are empty; a job event includes
``action`` only when a task name is supplied. The task action retains the task name followed by a
number sign (``#``) and the task identifier. It is not split into new fields.

The ``reference`` field commonly identifies a related event on another site, allowing events to be correlated across the system. Some existing callers supply a
resource identifier instead; the field does not establish that every reference identifies an event.

In the examples below, braces enclose each object, double quotes enclose field names and string values,
a colon separates each field name from its value, and commas separate fields. The event identifiers
distinguish individual events; the second example's reference points to the first event. The names
``trainer@b.org``, ``train.deploy``, ``training`` and ``job-1`` are illustrative user, command, scope and
job values. The task action ``train#task-1`` combines the task name ``train`` and identifier ``task-1``.

.. code-block:: json

    {"event_id": "16392ed4-d6c7-490a-a84b-12685297e912", "timestamp": "2026-11-16T12:59:47.691957+00:00", "user": "trainer@b.org", "action": "train.deploy"}
    {"event_id": "636ee230-3534-45a2-9689-d0ec6c90ed45", "reference": "16392ed4-d6c7-490a-a84b-12685297e912", "timestamp": "2026-11-16T15:08:33.181712+00:00", "scope": "training", "job": "job-1", "action": "train#task-1", "message": "received task from server"}

File Writing
^^^^^^^^^^^^
The default filename is ``audit.jsonl``. Callers that supply their own audit filename can use any
filename extension. The writer creates the file when needed and appends events when the service
restarts. It does not read or convert previously written records.

Each call waits for the local write and flush before returning the event identifier. Flushing passes
buffered data to the operating system; it is not a guarantee that the record will survive a machine
failure. Excluded actions are not written, and the simulator's auditor remains inactive.


Security and Administration Coverage
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
Administrator request records use the registered command name and exclude raw
arguments. Sensitive commands additionally record dispatch and handling results.
A handler returning does not establish that its requested operation completed.
Security records cover identity and session checks, permission decisions, client
administration, job deletion/abort, study membership, logging changes, scheduled
shutdown/restart, and protected downloads.

New records use only the eight fields above. Verified actors appear in ``user``;
before verification or when administrator attribution is unavailable, it is
``unknown``. Reasons and approved resource identifiers appear in ``message``.
Study identifiers belong in that message, while ``scope`` remains a job scope.
Server outcomes reference their request; client receipts reference the server
request, and client outcomes reference their local receipt.

Administrative recording failures allow the operation to continue and produce
independent, rate-limited diagnostics. The diagnostic count represents failed
attempts, not an exact number of lost records. Unrelated audit callers retain
their existing error behavior. Intentional simulator silence is not a failure.

Download terminal records describe only the transfer service's reported result;
they do not establish confirmed receiver receipt or successful extraction. The
direct job-log reply records preparation only, because it has no transfer-service
completion callback. Likewise, scheduled shutdown/restart and remote
acknowledgements do not prove that a program stopped or restarted. A handled
job-abort request likewise does not establish that an abort signal was dispatched.
Selected remote targets omitted from the reply list are recorded as no reply;
ambiguous empty job-child results and unknown site-logging reply codes are
recorded as unknown outcomes, rather than acknowledgements.

See the `security and administration event catalog
<../../../design/audit_security_admin_coverage.md>`_ for action names, capture
boundaries, attribution limits, and validation coverage.


Task Execution and Workflow Results
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
Task and workflow records retain the same eight possible fields. New actions
distinguish assignment preparation, executor handling, result preparation,
publication, complete receipt, callback processing, task retirement, and workflow
handling/finalization. A received result does not establish successful processing
or aggregation; an executor or callback returning does not prove training success.

Task records use the established local job/scope and ``unknown`` for an
unavailable administrator actor. Approved task identifiers appear in ``message``;
new records exclude task/result contents, credentials, paths and exception text.
New references come from records written by the same process. Existing task
audit headers and combined task actions keep their behavior. A direct task
outcome can come from a target or from the local transport. An omitted return
code is recorded as an unspecified outcome.

New records are buffered while shared locks are held and written afterwards.
Their timestamps are writing times, so they do not establish exact observation
order across workers. New recording failures allow the operation to continue;
existing unrelated and legacy audit caller failure behavior remains unchanged.

See the `task and workflow coverage contract
<../../../design/audit_task_workflow_coverage.md>`_ for capture owners, evidence
limits, failure behavior, dependencies and validation coverage. Model saving and
loading remain a later increment.
