# Trustee administrator credential security

Run these operations only on the trusted secure-services host. The KBS
administrator credential can change policies and resources; it must never be
delivered to the CoCo cluster owner or included in a public handoff.

## Fresh installation

The [pinned upstream setup script](https://github.com/confidential-containers/trustee/blob/338610fbfed57b66c61a8a3a60e0e4386bdce793/kbs/config/docker-compose/setup.sh)
enables shell tracing while creating a ten-year administrator JWT and explicitly
makes its token file mode `0644`. The trace contains all three JWT segments, which
can be reassembled into a usable bearer token. Turning off tracing in the outer
host script does not turn it off inside the setup container.

Stage `05-deploy-trustee.sh` now calls `lib/harden-trustee-setup.py` **before**
Compose can run setup. The helper checks the whole upstream script against its
reviewed SHA-256, accepts only that source or the exact already-hardened variant,
and atomically updates the actual bind-mounted script. Unknown source fails
closed. The hardened setup script:

- disables tracing itself, including when its shell was invoked with `-x`;
- preserves `errexit`, `nounset`, and `pipefail`, so setup failures still fail;
- sets `umask 077` before creating any key, token, or signing temporary file;
- restricts the key directory to `0700`, existing private keys/token to `0600`,
  and leaves the new administrator token at `0600` from creation onward.

The setup status message names a file but does not print its contents. KBS, AS,
and setup still run with the pinned Compose configuration. The administrator
signing key/token, AS signing key, and CA private key stay on this host; only the
appropriate public certificates/keys go to other parties.

## Existing installations: rotate an exposed administrator credential

Applying the source patch or changing file permissions **does not invalidate a
token already copied from logs**. Treat administrator credentials generated by
the old setup as exposed. Generating another token with the same signing key also
does not revoke an old token. Rotate the Ed25519 administrator signing key and
make KBS reload the replacement public key. This invalidates all tokens signed
by the retired key, including tokens minted by other administrators using it.

Use a maintenance window: administrative operations and new key releases will
be unavailable while KBS is stopped. Already-running guests are not retroactively
revoked. Coordinate with every authorized administrative token holder. Do not
restore the old public key as a rollback; that would re-enable leaked tokens.

**Do not rerun stage 05 merely to rotate credentials.** It resets the active
resource policy to default-deny. The narrower commands below leave resource
policies, stored workload keys, RVPS references, AS policy/signing material,
registry credentials, and HTTPS TLS certificates unchanged. Start from an
existing healthy installation and the updated service-kit checkout containing
this helper; `platform.env` must refer to that installation.

### 1. Patch setup and stop KBS before changing credentials

Run the following in a Bash shell from the service-kit directory. Do not use
`bash -x`, print token files, or export tokens into command-line arguments. Keep
the shell open for the following steps; variables are reused.

```bash
set +x
set -Eeuo pipefail
umask 077
source ./lib/common.sh
python3 ./lib/harden-trustee-setup.py \
  "${TRUSTEE_ROOT}/kbs/config/docker-compose/setup.sh"

key_dir="${TRUSTEE_ROOT}/kbs/config/docker-compose"
policy_before="$(sudo sha256sum "${KBS_POLICY_DIR}/resource-policy.rego")"
sudo docker compose -p "${TRUSTEE_PROJECT}" -f "${TRUSTEE_COMPOSE}" stop kbs
retired="$(sudo mktemp -d "${TRUSTEE_ROOT}/.retired-admin-credentials.XXXXXX")"
sudo chmod 0700 "${retired}" "${key_dir}"
sudo chmod 0600 "${key_dir}/private.key" "${key_dir}/admin-token"
for file in private.key public.pub admin-token; do
  sudo mv -- "${key_dir}/${file}" "${retired}/${file}"
done
```

The root-only retirement directory temporarily retains the old credential for
the negative verification below and any required incident investigation. Never
copy it into a handoff or a shared backup. If any command fails after stopping
KBS, leave KBS stopped, investigate, and finish the rotation before resuming.

### 2. Generate replacement administrative material and reload KBS

The one-off setup uses the patched bind-mounted script. Existing `token.key`
means upstream setup leaves the AS signing key/certificate chain unchanged.

```bash
sudo docker compose -p "${TRUSTEE_PROJECT}" -f "${TRUSTEE_COMPOSE}" \
  run --rm --no-deps setup
sudo chown root:root "${key_dir}/private.key" "${key_dir}/admin-token"
sudo chmod 0600 "${key_dir}/private.key" "${key_dir}/admin-token"
sudo docker compose -p "${TRUSTEE_PROJECT}" -f "${TRUSTEE_COMPOSE}" \
  up -d --no-deps --force-recreate kbs
wait_https "${KBS_URL}/healthz" "${TRUSTEE_PUBLIC_CERT}" 120
[[ "$(sudo sha256sum "${KBS_POLICY_DIR}/resource-policy.rego")" == "${policy_before}" ]]
```

`--no-deps` deliberately avoids recreating AS/RVPS or starting the old setup
container. Recreating KBS reloads the new public key at the same trusted-issuer
path. The issuer and required `KBS` audience do not change.

### 3. Verify acceptance of the new token and rejection of the old token

This is a read-only request to the administrator policy endpoint. It uses TLS
verification, disables proxies and redirects, and never prints token values or
policy contents. It must report `new: HTTP 200`, `retired: HTTP 401`, and
`anonymous: HTTP 401`. Unexpected responses fail the check.

```bash
sudo python3 - "${KBS_URL}" "${TRUSTEE_PUBLIC_CERT}" \
  "${key_dir}/admin-token" "${retired}/admin-token" <<'PY'
import ssl
import sys
import urllib.error
import urllib.request
from pathlib import Path

class NoRedirect(urllib.request.HTTPRedirectHandler):
    def redirect_request(self, req, fp, code, msg, headers, newurl):
        return None

url, cert, current, retired = sys.argv[1:]
opener = urllib.request.build_opener(
    urllib.request.ProxyHandler({}),
    urllib.request.HTTPSHandler(context=ssl.create_default_context(cafile=cert)),
    NoRedirect(),
)
for label, path, expected in (
    ("new", current, 200), ("retired", retired, 401), ("anonymous", None, 401)
):
    headers = {"Authorization": "Bearer " + Path(path).read_text().strip()} if path else {}
    request = urllib.request.Request(url.rstrip("/") + "/kbs/v0/resource-policy", headers=headers)
    try:
        with opener.open(request, timeout=15) as response:
            status = response.status
    except urllib.error.HTTPError as error:
        status = error.code
    print(f"{label}: HTTP {status}")
    if status != expected:
        raise SystemExit(f"Administrator credential rotation check failed for {label}")
PY
```

If the retired token still succeeds, stop KBS again and investigate its active
configuration and every trusted issuer/key. Do not announce successful rotation.
Replace any authorized administrators' copies with newly minted credentials over
their approved private channel. The normal service-kit tools use `ADMIN_TOKEN`
at its unchanged path and require no workload-owner/CoCo changes.

### 4. Handle historical logs and retired secrets

The patch does not sanitize already-captured logs. Restrict their access and
inspect configured Docker logging drivers, log collectors, exports, and backups
under your incident-retention policy. Do not paste old setup logs into tickets.
After securely preserving any required evidence, remove the old stopped setup
container and its Docker-managed local logs:

```bash
sudo docker compose -p "${TRUSTEE_PROJECT}" -f "${TRUSTEE_COMPOSE}" rm -f setup
```

This command does not delete bind-mounted keys or policies, and does not erase
copies retained by external log drivers/collectors/backups. Restrict or purge
those copies separately according to policy. Retire the root-only old credential
directory under the same policy; never trust its public key again. Revocation
depends on the successfully verified key rotation, not on complete log erasure.

## Validation scope

The regression tests execute the checksum-matched upstream script and its
hardened version with disposable OpenSSL keys, including inherited Bash and
BusyBox ash tracing. They reproduce the old JWT-fragment disclosure, verify its
absence after hardening, check private modes (including observations before the
final token `chmod`), reject unknown/linked source, and preserve setup failures.
They do not contact a live Trustee. The rotation procedure above must be verified
against the operator's actual deployed KBS before declaring an incident resolved.
